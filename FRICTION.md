# Friction log: using Sim as a customer

Plain list, dated. What was hard, confusing, or surprising. No fixes to Sim's code.

- 2026-09-24: Docs for logs (docs.sim.ai/execution/logging) point to the API reference, and the API reference page lists endpoint names without params. The per-run endpoint (`GET /api/v2/logs/{runId}`, `includeTraceSpans` on the list endpoint) is only discoverable from `/openapi.json`.
- 2026-09-24: API reference says base URL is `https://www.sim.ai` with no note on what changes for a self-hosted install.
- 2026-09-24: `sim-setup@1.0.28` Quick mode warned that the Docker VM had 3.8GB and recommended 8GB+. Useful catch, but the README only says "Node 20+ and Docker" and never mentions memory, so a customer would first find out mid-wizard.
- 2026-09-24: The wizard detects a shell LLM key (ANTHROPIC_API_KEY), then separately asks to "Generate your Chat API key in the browser". It isn't clear from the wizard whether Chat needs a sim.ai cloud account on a self-hosted install, or whether the detected key covers it.
- 2026-09-24: `npx sim-setup status` reports `postgres (sim-postgres): absent` and `redis (sim-redis): absent` while both containers are running and healthy. The actual names are `sim-<hash>-db-1` and `sim-<hash>-redis-1` (Compose project prefix), so status looks up the wrong names. A customer would reasonably think their database failed to start.
- 2026-09-24: The Compose file pins every Sim image to `:latest` by default (`SIM_VERSION` unset). A self-hosted customer can't tell which version they're running without inspecting image digests, and `update` will silently change it. Recorded digests in SIM_VERSION.txt.
- 2026-09-24: The wizard detected ANTHROPIC_API_KEY and wrote it to `.env`, but on a self-hosted install the Agent block still asks for its own API key. From the shipped bundle, server-side provider keys appear to apply only when `isHosted`, and the Anthropic key-rotation config has no `ANTHROPIC_API_KEY` fallback, unlike OpenAI and Gemini. (Read from minified code, not confirmed in source.) A customer reasonably expects the key they gave setup to be used.
- 2026-09-24: The block picker shows both "Agent" and "Claude Managed Agents". When you're looking for how to call Claude, it's easy to pick the wrong one.
- 2026-09-24: After deploying, I couldn't find the workflow ID in the UI. I got it from the database instead. (It's also the last segment of the editor URL, `/workspace/<ws>/w/<workflowId>`.) The API docs require `{workflowId}` in every call, so it should be one click away from Deploy.
- 2026-09-24: A synchronous execute returns `status: completed`, but `GET /api/v2/logs/{runId}` called right after still returns `status: running` and `endedAt: null`. The log is finalized about 2ms later. The docs don't mention it, and a harness that reads logs immediately after execute gets empty timings. Workaround: poll until the status is final.
- 2026-09-25 (corrected 2026-09-25): A new Agent block created in the editor gets temperature 0.3 (seen in two workflows). The provider falls back to 0.7 only when the value is null (`request.temperature ?? 0.7` in `providers/anthropic/core.ts`), for example a block created without the editor. Neither is 0, which is what a classification workflow wants, and the two different defaults are easy to miss. The slider is also `mode: 'advanced'` in `blocks/blocks/agent.ts`, so it's hidden until you click "Show additional fields"; a customer who never opens it runs at 0.3 without seeing it. The first version of this note wrongly said the editor default was 0.7.
- 2026-09-25: Structured output is enforced natively only for models flagged `nativeStructuredOutputs` in `providers/models.ts`. Other models get the schema as prompt text, with only an info-level server log (`Using prompt-based structured outputs`). A customer who switches models, or whose `fallbackModels` kick in, silently loses schema enforcement. String-length limits (`maxLength`) are never grammar-enforced, even natively.
- 2026-09-25: Running `npx sim-setup stop` from another directory prints "No Sim install detected. Run npx sim-setup first.", which suggests installing again. The install is found only when you run from the parent of the `sim/` folder. A customer following that message might run setup a second time. The same run also showed that `npx sim-setup` resolves to the latest version (1.0.29 today, 1.0.28 yesterday), so the management tool can change version between commands.
- 2026-09-25: On a self-hosted install, each run's logged cost includes a fixed $0.005 `execution_fee` ("Base Run" in the UI). `logging-factory.ts` defaults `baseExecutionCharge` to `BASE_EXECUTION_CHARGE = 0.005`, while actual billing is gated on `isBillingEnabled`. For a Haiku triage run (about $0.0018 in model cost), the logged total ($0.0068) is about 3.8x what the provider bills. A self-hosting customer tracking spend from Sim's logs would overstate it. (Inferred from source plus our logs; not confirmed with the Sim team.)
- 2026-09-25: The Evaluator block docs (docs.sim.ai/blocks/evaluator) say the default model is `claude-sonnet-4-6`, and that temperature and a system prompt are "available under advanced". In the running image and on `main`, the default is `claude-sonnet-5`, both fields are `hidden: true` in `blocks/blocks/evaluator.ts`, temperature is fixed at `EVALUATOR.DEFAULT_TEMPERATURE = 0.1`, and the system prompt is generated from the metrics. A customer can't make the judge deterministic or give it instructions except through the content. The generated prompt also asks for "only scores" with no reasoning, which the docs don't mention.
- 2026-09-25: Batch-running a deployed workflow through `POST /api/v2/workflows/{id}/execute` with 4 concurrent synchronous calls on a self-hosted install produced `429 RATE_LIMITED` ("API rate limit exceeded", with `details.retryAfter`) for 39 of about 750 calls, all in one burst. The response is well-formed and gives a retry time, which is good. But the deployment docs don't say what the limits are for a self-hosted instance or how to raise them, so a customer's batch job fails without warning. The harness now waits until `retryAfter` and retries, and reports the count.
